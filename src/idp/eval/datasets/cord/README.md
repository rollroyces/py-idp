# CORD eval dataset (py-idp v0.4)

This directory is a **synthetic-but-faithful** CORD-shape eval set
for py-idp's `Receipt` schema. It exists to give the v0.4 release
(C2 in `docs/ROADMAP_v0.4.md`) a real, reproducible baseline with
per-field precision / recall / F1 numbers — not a hand-waving
"the model got it right" smoke test.

## What's in here

| file / dir | purpose |
|---|---|
| `docs/*.txt`              | 30 synthetic receipt text fixtures, modelled on the CORD shape (Park et al., 2019). |
| `manifest.json`           | Per-doc `{doc_path, schema, gold}` entries; the eval runner reads this via `tests/eval_cord/manifest_adapter.py`. |
| `README.md`               | This file. |
| `LICENSE.txt`             | Verbatim CC-BY-4.0 text — the upstream license declared in the CORD repository's README. |
| `ATTRIBUTION.md`          | Verbatim BibTeX for the CORD paper; required citation when redistributing. |

## License

The CORD dataset is published under the Creative Commons Attribution
4.0 International License (CC-BY-4.0) — see the upstream README at
<https://github.com/clovaai/cord>. The 30 fixtures here reproduce the
CORD schema and so inherit that license for redistribution purposes;
the verbatim CC-BY-4.0 text is bundled in `LICENSE.txt` and the
verbatim citation is in `ATTRIBUTION.md`.

The fixtures themselves are **synthetic** — they were authored from
scratch to exercise the `Receipt` schema (CORD JSON shape: merchant
header, line items, subtotal / tax / tip / total, payment method,
last-4 card). No string is copied verbatim from any specific
receipt in the public CORD release.

## Loading the dataset

The `idp.eval.runner` reads `cases.jsonl`. This directory ships
`manifest.json` instead, because that is the cleaner human-editable
shape (one JSON object per doc, easy to diff, easy to grep). A
thin adapter in `tests/eval_cord/manifest_adapter.py` materialises
`manifest.json` into the `cases.jsonl` shape at test time. The
runner itself is unchanged.

To run the eval against the in-tree MockBackend:

```bash
pytest tests/test_eval_cord.py -v
```

To run against a real backend (Ollama, OpenAI, Anthropic), set
`IDP_EVAL_BACKEND`:

```bash
IDP_EVAL_BACKEND=ollama pytest tests/eval_cord/test_eval_real_dataset.py -v
```

The slow-marked real-backend test is skipped on the default CI
suite; see "Slow tests" below.

## Schema coverage

The 30 fixtures span the common CORD shapes:

| shape | fixtures |
|---|---|
| cafe / coffee                       | 001, 011, 013, 029 |
| quick-service restaurant            | 002, 018, 021 |
| restaurant with tip                 | 003, 007, 014 |
| grocery / pharmacy / convenience    | 004, 008, 009 |
| specialty retail (books, wine, etc.) | 005, 012, 016, 019, 022 |
| auto / gas / parking                | 006, 010, 017, 028 |
| hotel / movie / bar                 | 020, 026, 030 |
| pet / hardware / smoothie / dry-clean / ice cream / donut | 015, 023, 024, 025, 027 |

A few fixtures deliberately exercise edge cases of the `Receipt`
schema:

- `receipt-006.txt`, `receipt-010.txt`: zero `line_items` (parking,
  gas) — tests the `Field(default_factory=list)` path.
- `receipt-008.txt`: OCR-noisy text (`O → 0`, `l → 1`) — tests
  robustness to common OCR substitutions. Ground truth is the
  *intended* post-OCR-correction values.
- `receipt-018.txt`, `receipt-027.txt`, `receipt-029.txt`: `Cash`
  payment, `credit_card_last4 = null` — tests the optional
  credit-card field.
- `receipt-009.txt`, `receipt-011.txt`: line items with quantity
  `> 1` — tests `ReceiptLineItem.quantity` and `total` arithmetic.

## Slow tests

The real-backend test (`tests/eval_cord/test_eval_real_dataset.py`)
is marked `@pytest.mark.slow` and does NOT run on the default CI
suite. Run it manually with `IDP_EVAL_BACKEND=<name>` to refresh
the per-backend numbers in `docs/eval/BASELINE.md`. CI skips it via
`pytest -m "not slow"` in the default run.

The slow marker is registered in `pyproject.toml` under
`[tool.pytest.ini_options].markers`.

## Reproducing the baseline numbers

The README claims in `docs/eval/cord.md` are regenerated by:

```bash
pytest tests/test_eval_cord.py -v
# then run the helper script that copies the row into docs/eval/BASELINE.md:
python tests/eval_cord/update_baseline_doc.py
```

Both run without any API key (MockBackend is deterministic and
offline).

## What's NOT in scope for v0.4

- Per-template baselines (e.g. one number per merchant category) —
  the eval reports the aggregate over all 30 fixtures. Per-template
  breakdown is v0.5 work.
- Automated regression gating (`fail CI if F1 drops > 5%`). The slow
  test asserts a *lower bound* for the MockBackend only; real-backend
  drift detection is v0.5 because it needs the threshold number from
  real CORD results, which we don't have at v0.4 cut.
- CORD's original ~1000 receipts. We're using 30 synthetic
  fixtures, scoped to the 1-day v0.4 budget. The manifest format
  is forward-compatible: dropping in the real CORD receipts (and
  their ground truth) is a mechanical converter + a larger `n_docs`
  number, no schema changes.
